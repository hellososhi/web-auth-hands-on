# 第8章 新しい機能に応用する

[← 第7章 ブラウザの仕組みを使った攻撃と防御](07-browser-security.md) · [目次](README.md) · [付録A テストの読み方・書き方 →](appendices/testing.md)

## この章の目標

認証・認可・入力検証・テストを、新しい機能にも適用します。自作した処理を、Better Authで使った機能と対応付けます。

## 応用課題：表示名を変更する

利用者のプロフィールに、ログイン用のユーザー名とは別の表示名を追加します。

- 表示名を保存するためにUserモデルを変更する。
- `PATCH /api/profile` で、自分の表示名を変更できる。
- 利用者IDはセッションから取得する。
- 入力は表示名だけを受け付ける。
- 入力に他人のユーザーIDを追加した場合は `400` にする。
- 未認証なら `401` にする。
- 第7章のOrigin検証を適用する。
- レスポンスには公開用プロフィールだけを返す。

## 設計・実装・確認

1. Prismaモデルの変更とマイグレーションを作成してください。
2. APIと画面を追加してください。
3. 自分の表示名を更新できることを確認してください。
4. 未認証と不正な入力のケースをテストしてください。
5. 拒否された場合にユーザー情報が変化しないことを確認してください。

## Better Authと対応付ける

次の処理について、自作したコードの場所と、以前使ったBetter Authの機能を対応付けてください。

- ユーザーの登録。
- パスワードの保存・照合。
- セッションの発行・確認。
- Cookieの設定。
- ログアウト・有効期限。

Better Authは、Cookieを使ったセッション管理や期限管理を提供します。今回作った処理の対応を確認し、ライブラリに任せる責務を説明してください。

メモの所有者を決め、誰にどのメモの操作を許すかは、このアプリの仕様です。認証ライブラリを使う構成でも、その仕様をアプリ側で実装・確認します。

参考：[Better Authのセッション管理][ref-better-auth]、[OWASPの認可ガイド][ref-authorization]

## 最終説明課題

コードとNetworkタブを使って、次の内容を説明してください。

1. ログインからメモ取得まで、ブラウザ・API・DBで何が起きるか。
2. 正しいパスワードを入力したことを、後のリクエストとどう結び付けるか。
3. AがBのメモを更新しようとしたとき、どの条件で拒否するか。
4. ログアウトしたトークンを再送しても使えない理由。
5. 実装を変更した後、何をテストすれば仕様が維持されたと確認できるか。

## 最終確認

- [ ] 登録・ログイン・再読み込み・ログアウトを続けて操作できる。
- [ ] 未認証・他人のメモ・期限切れ・失効済みトークンを拒否できる。
- [ ] 拒否された更新で、DBが変更されない。
- [ ] 不正なOriginからの状態変更を拒否できる。
- [ ] JSONレスポンスやログにパスワード・保存用ハッシュ・セッショントークンを出していない。
- [ ] 新しいプロフィール機能にも、必要な検証が適用されている。
- [ ] 自分の実装と、それを確認するテストを説明できる。
