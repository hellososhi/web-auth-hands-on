# 第5章 自分のメモを守る

[← 第4章 セッションを設計してログインを続ける](04-sessions.md) · [目次](README.md) · [第6章 ログイン状態を終了させる →](06-logout-and-expiration.md)

## この章の目標

メモの所有者を保存し、ログインした利用者が自分のメモだけを操作できるようにします。

## 実装する仕様

- メモAPIの利用には、有効なセッションが必要。
- メモの所有者は、セッションから取得したユーザー。
- 作成・更新の入力は、許可した項目だけを受け付ける。
- 作成リクエストに `ownerId` を含めた場合は、入力不備として `400` にする。
- メモ一覧には、自分のメモだけを含める。
- 他人のメモの取得・更新・削除は `404` にする。
- 存在しないメモも `404` にする。

未認証のリクエストは `401` です。ここでは、非公開メモの存在を区別して返さない方針として `404` を選びます。HTTPステータスとアプリの公開範囲を合わせて決めます。

## なぜ所有者をサーバーが決めるのか

クライアントが送った所有者IDを採用すると、他人のIDを指定してメモを作れます。認証で取得した利用者IDを使えば、サーバーが検証した利用者と所有者を結び付けられます。

IDを推測しにくくしても、所有者の確認は必要です。URLなどから他人のメモIDを知った場合にも、そのデータを操作させないためです。

参考：[OWASPの認可ガイド][ref-authorization]

## 設計課題：Noteに所有者を追加する

`Note` に所有者への参照を追加し、UserとNoteの関係を定義してください。完成後のメモは必ず1人の所有者に属する仕様です。

初期のサンプルメモには所有者がありません。所有者を必須にする前に、教材用のメモをいったん0件にします。その後、新しいモデルに合わせてA・Bのユーザーとそれぞれのメモを作り直します。

既存データを残すアプリでは、各メモを誰のものにするかという移行方針が必要です。この教材の初期化は、作り直せるサンプルデータを前提にした手順です。

作業は次の順番で進めます。

1. 現在のモデルのまま `pnpm db:studio` を起動します。接続先が教材の `prisma/dev.db` であることを確認し、`Note` の教材用データをすべて削除して、0件にします。
2. Prisma Studioと開発サーバーを停止します。
3. 設計した必須の所有者への参照を `schema.prisma` に追加し、`pnpm db:migrate --name add-note-owners` を実行します。既存のメモが0件なので、所有者未設定の行は残りません。
4. `prisma/seed.ts` を、新しいモデルに合わせてA・Bのユーザーと所有者付きメモを作る内容へ変更します。パスワードの保存には、自分で作ったハッシュ関数を使います。
5. 新しいマイグレーションとseedが揃ってから、ターミナルで `pnpm db:reset` を実行し、表示された接続先を確認して `RESET` と入力します。新しい構造でDBが作り直され、更新したseedが実行されます。

`pnpm db:reset` は初期化後にseedも実行します。手順1の代わりに最初からresetすると、元の所有者なしメモが再投入されます。また、resetは保存済みマイグレーションを適用するコマンドです。モデル変更の履歴を作る手順3を先に行います。

## 実装課題：認証必須処理

`require-user.ts` に、次の処理を作ります。

1. Cookieからトークンを読む。
2. 有効なセッションを取得する。
3. 未認証なら `401` を返す。
4. 認証済みなら、後続の処理から利用者を参照できるようにする。

Honoのコンテキストに利用者を渡し、メモの各ルートで利用します。DBのパスワードハッシュをコンテキストやレスポンスへ広く渡さず、必要な項目だけを使います。

## 実装課題：すべてのメモ操作に適用する

- 一覧：所有者が自分のメモを検索する。
- 作成：所有者を現在の利用者に設定する。
- 詳細：メモIDと自分の所有者IDの両方に合うメモを取得する。
- 更新・削除：メモIDと所有者IDの条件に合うデータだけを変更する。

更新・削除では、DB操作自体にも所有者の条件を含めてください。指定したメモが対象にならなかった場合は `404` を返します。

## 手動確認

1. Aでログインしてメモを作り、IDを控えます。
2. 別プロファイルでBとしてログインします。
3. Bの一覧にAのメモが表示されないことを確認します。
4. BからAのメモIDを指定し、取得・更新・削除を試します。
5. Aに戻り、メモが変わっていないことを確認します。
6. CookieなしでもメモAPIを直接呼び、拒否されることを確認します。

## 自動テスト：拒否された後のDBを見る

AのセッションとBのメモを用意し、AからBのメモを更新するリクエストを送ってください。

確認するのは、次の二つです。

1. レスポンスが `404`。
2. Bのメモの内容が変更前と同じ。

エラーを返していても、その前にDBを変更するバグがあれば、二つ目の確認で検出できます。

同じ考え方で、未認証の作成が `401` となりメモが増えないこと、他人の削除が拒否されメモが残ることを確認します。

配布時の `tests/notes.test.ts` は、未認証でもメモを操作できる仕様を確認しています。この章では、成功するケースにユーザーとセッションの準備を追加し、新しい仕様へ書き換えます。モデル間に参照を追加したため、テストデータの作成・削除順も確認してください。

## 完了条件

- [ ] 一覧・詳細・作成・更新・削除すべてに、認証と所有者のルールがある。
- [ ] 自分のメモを正常に操作できる。
- [ ] 他人のメモを取得・変更できない。
- [ ] リクエストの `ownerId` を書き換えても、他人名義で作成できない。
- [ ] 画面の表示制御とAPIのアクセス制御の役割を説明できる。
