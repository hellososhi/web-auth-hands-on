# 第3章 パスワードを確認する

[← 第2章 ユーザー登録とパスワード保存](02-registration-and-passwords.md) · [目次](README.md) · [第4章 セッションを設計してログインを続ける →](04-sessions.md)

## この章の目標

登録した認証情報を照合し、成功・失敗を返す処理を作ります。その後、次のリクエストでも同じ利用者だと判断する方法を考えます。

## 実装する仕様

`POST /api/auth/login` にユーザー名とパスワードを送ります。

- ユーザー名に対応するユーザーを検索する。
- 保存済みハッシュと入力パスワードを照合する。
- 照合成功時は `200` と公開用のユーザー情報を返す。
- ユーザーが存在しない場合と、パスワードが誤っている場合は、同じ `401` とエラーコードを返す。
- この章では、ログイン成功後のCookieとセッションの発行をまだ追加しない。

入力の形式が不正な場合は `400` です。サーバーやDBの障害は内部エラーとして扱います。認証情報の不一致と、システムの故障は別の条件です。

## なぜ失敗の理由をまとめるのか

「ユーザーが存在しません」と「パスワードが違います」を分けると、ログイン画面を使って登録済みユーザーを調べられます。この教材では、ログイン失敗のステータス・エラーコード・画面表示を統一します。

処理時間の違いから情報が分かる場合もあります。基本課題では応答を揃え、処理時間については第7章の読解で扱います。

参考：[OWASPの認証ガイド][ref-authentication]

## 実装課題

1. ログインAPIを追加してください。
2. 第2章の `verifyPassword` を利用してください。
3. ログイン画面を作り、Hono RPCで呼び出してください。登録成功後に、この画面へ進めるようにしてください。
4. 成功時・失敗時の表示を作ってください。
5. 不正な入力と、認証情報の不一致を区別して処理してください。

## 確認課題

正しい情報、誤ったパスワード、存在しないユーザー名の3通りを試します。後ろの2通りのステータスと本文を比較してください。

APIの自動テストを最初に1件、講師と書きます。Honoの `app.request()` を使い、入力を送ってレスポンスを確認します。JSONのリクエストには対応する `Content-Type` を付けます。更新系のテストでは、この段階から `Origin` も指定し、第7章で送信元確認を追加した後も同じ形式を使います。

参考：[HonoのAPIテスト][ref-hono-testing]、[Honoの入力検証][ref-hono-validation]

APIテストの準備には、[既存のメモAPIテスト](../tests/notes.test.ts)と同じ `createTestContext()` を使えます。`context.app.request()` にリクエストを渡し、`context.prisma` でテスト用ユーザーを作成します。更新系で使う `Origin` の指定も、既存テストの `jsonHeaders` を参考にしてください。

## 考えてみよう：次のリクエストは誰のものか

正しいパスワードを送ると成功のレスポンスが返ります。その後、新しいリクエストでメモ一覧を取得します。

そのリクエストの中に、先ほどパスワードを確認した利用者だと判断できる情報はありますか。ページを再読み込みした場合も調べてください。

画面にユーザー名を表示できても、サーバーは次のリクエストを検証するための情報を必要とします。次の章では、ログイン成功時に秘密のトークンを発行し、その情報で複数のリクエストを結び付けます。

## 完了条件

- [ ] 正しい認証情報なら成功し、誤った情報なら失敗する。
- [ ] 存在しないユーザーと誤ったパスワードで、ログイン失敗の応答が同じになる。
- [ ] 「パスワードの照合」と「次のリクエストでも利用者を判断すること」の違いを説明できる。
