# 第1章 認証のないアプリを調べる

[← 準備：テンプレートを動かす](setup.md) · [目次](README.md) · [第2章 ユーザー登録とパスワード保存 →](02-registration-and-passwords.md)

## この章の目標

今のアプリが「誰の操作か」を判断していないことを確認し、完成後に必要なルールを言葉にします。

## 観察課題：何が送られているか

1. メモを1件作成します。
2. Networkタブで、作成のリクエストを選びます。
3. URL、HTTPメソッド、リクエスト本文、ステータス、レスポンス本文を確認します。
4. 別のターミナルで `pnpm db:studio` を実行し、Prisma Studioの `Note` から、そのメモを探します。
5. 別のブラウザ、または別プロファイルでもアプリを開きます。
6. 先ほどのメモを読めるか、編集できるかを確かめます。

ここで見つけてほしいのは、「メモの内容は送っているが、操作するアカウントを確認する仕組みがない」という状態です。

## 完成後の仕様を決める

この教材では、完成後のメモを次のように扱います。

- ログインした利用者だけがメモAPIを使える。
- メモを作成した利用者が、そのメモの所有者になる。
- 所有者だけが、そのメモを閲覧・更新・削除できる。
- ログアウトしたセッションのトークンでは、保護APIを使い続けられない。

**課題：必要な情報を列挙してください。**

「利用者を保存するには何が必要か」「メモと利用者を何で結び付けるか」「リクエストから利用者を判断するには何が必要か」を考えてください。具体的なPrismaモデルを書くのは次の章からです。

## 信用する情報の境界

ブラウザから送るJSONやURLは、送信者が変更できます。

例えば本文に `{ "userId": "A" }` と書かれていても、その文字列だけでAさんと判断すると、他の人もAさんを名乗れます。サーバーは、提示された認証情報を検証して利用者を判断する必要があります。

認可では、さらに「その利用者が、そのメモを操作してよいか」をDBの情報に基づいて確認します。

参考：[OWASPの認可ガイド][ref-authorization]

## 説明課題

- 今のメモAPIは、利用者をどう区別していますか。
- 画面の編集ボタンを消した場合、APIへの直接リクエストも拒否されますか。
- クライアントから送られた `userId` をそのまま採用すると、どんな操作が可能になりますか。

## 完了条件

- [ ] メモ作成のリクエストと、DBの保存結果を対応付けられる。
- [ ] 完成後に許可する操作と、拒否する操作を説明できる。
- [ ] ブラウザからの自己申告と、サーバーで検証した情報を区別できる。
