# 第4章 セッションを設計してログインを続ける

[← 第3章 パスワードを確認する](03-verifying-passwords.md) · [目次](README.md) · [第5章 自分のメモを守る →](05-authorization.md)

## この章の目標

`Session` モデルを設計し、ログイン成功時に発行したトークンから利用者を取得できるようにします。

## セッションの考え方

ログイン成功時にサーバーが予測困難なトークンを作ります。ブラウザにはトークンを渡し、サーバー側には、そのトークンと利用者の対応を保存します。

その後のリクエストでは、トークンが有効かをサーバーが確認します。この教材では、ブラウザ側の保管・送信にCookie、サーバー側の保存にDBを使います。

トークンを持っている人は、そのログイン状態を利用できます。トークンは秘密情報として扱います。

## 提示する仕様

- ログインに成功するたびに、新しいトークンを発行する。
- トークンは暗号用途の乱数APIで32バイトを生成し、64文字の小文字16進文字列にする。
- DBにはトークンのSHA-256ハッシュを保存する。
- ハッシュ対象は、Cookieに入れる64文字の文字列をUTF-8にした値とする。
- 1人のユーザーが複数のセッションを持てる。
- セッションごとに有効期限を持つ。
- 有効期限を過ぎたセッションでは、利用者を取得できない。
- この教材の有効期間は、発行から1時間に固定する。1時間は教材上の設定値で、自動延長は行わない。
- リクエストに含まれていた任意のトークンを、新しい有効なセッションとして採用しない。

暗号乱数の生成とSHA-256には `node:crypto` を使います。APIの候補は `randomBytes` と `createHash` です。

参考：[Node.jsのCrypto API][ref-node-crypto]

## なぜDBにトークンのハッシュを保存するのか

DBの保存値をそのままCookieに入れてログインできると、セッション表の読み取りだけで、残っているセッションを利用されます。ハッシュを保存しておけば、その保存値は元のトークンと異なります。

パスワードは人が選ぶため、候補を予想して試せます。一方、ここでは暗号乱数で作った十分長いトークンを使います。この違いから、パスワードにはArgon2id、トークンの保存・検索にはSHA-256を使います。

参考：[OWASPのセッション保存ガイド][ref-session-management]

## 設計課題：Sessionモデル

次の要求から、必要な項目を考えてください。

| 要求 | 考えること |
| --- | --- |
| 利用者を取得する | どのユーザーに属するかを、何の項目で表すか |
| 複数端末でログインする | UserとSessionは、どのようなリレーションになるか |
| トークンから検索する | 何を保存し、どの値に一意制約を付けるか |
| 期限切れを判断する | どの型で期限を保存するか |
| 1件だけログアウトする | どのセッションを特定して削除するか |

まず項目名・型・制約を紙やメモに書き、理由を説明してください。その後にPrismaモデルとマイグレーションを作成します。

モデルを書いたら `pnpm db:migrate --name add-sessions` を実行します。マイグレーションの適用後、クライアントも再生成されます。

**設計を確認する観点**

- UserとSessionは1対多になっているか。
- `userId` を一意にして、1人1セッションに制限していないか。
- `tokenHash` を一意に検索できるか。
- 利用者への参照と有効期限を必須にしているか。
- DBの行を識別するIDと、ブラウザが持つ秘密のトークンの役割を説明できるか。

主キーを別に設けるか、トークンのハッシュを主キーにするかは、設計理由を説明した上で決めてください。完成したモデルのコードは、設計後に講師の例と比較します。

参考：[Prismaの1対多リレーション][ref-prisma-relations]

## 実装課題：トークンとセッションの関数

次の役割を持つ関数を作ってください。具体的な型は、設計したPrismaモデルに合わせます。

- `generateSessionToken()`：暗号乱数からトークンを生成する。
- `hashSessionToken(token)`：トークンのSHA-256ハッシュを小文字16進文字列で返す。
- `createSession(userId, now)`：新しいセッションを保存し、Cookie設定に使う元のトークンと有効期限を返す。
- `findValidSession(token, now)`：有効なセッションと公開用の利用者情報を取得する。有効なものがなければ `null` を返す。

`now` は、現在時刻を表す `Date` です。本番の呼び出しではサーバー時刻を使い、テストでは指定した時刻を渡せるようにします。ブラウザが送った時刻を期限判定に使いません。

`findValidSession` の仕様は次のとおりです。

1. トークンがない・形式が違う場合は未認証にする。
2. トークンをハッシュ化してDBを検索する。
3. セッションがない場合は未認証にする。
4. `expiresAt <= now` の場合は未認証にする。
5. 対応するユーザーが存在しない場合は未認証にする。
6. 条件を満たした場合だけ、そのユーザーとして扱う。

有効期限の比較は、`Date` の時刻値に揃えてください。`null` の戻り値を、後のAPIで `401` に変換します。

## 実装課題：Cookieを設定する

第3章のログインAPIに、セッション発行を追加します。パスワード照合に成功した後でセッションを保存し、レスポンスの `Set-Cookie` で元のトークンを渡してください。

Cookieの名前は教材内で `session` に統一し、次の属性を使います。

- `HttpOnly`
- `SameSite=Lax`
- `Path=/`
- `Domain` は指定しない
- HTTPS環境では `Secure`
- DBのセッション期限と対応する `Max-Age` または `Expires`

この教材のローカルHTTPでは、開発用の設定を使います。Cookie属性を切り替える条件はリポジトリの設定にまとめます。

`HttpOnly` はページのJavaScriptから値を読むことを防ぎます。条件に合うAPIリクエストには、ブラウザがCookieを送信します。フロントエンドにトークンをJSONで返して保存させる処理は作りません。

参考：[MDNのSet-Cookie][ref-cookie]、[HonoのCookieヘルパー][ref-hono-cookie]

## 実装課題：現在の利用者を返す

`GET /api/auth/me` を作ります。Cookieからトークンを取得し、セッションを検証してください。

- 有効な場合：`200` と `{ user: { id, username } }`。
- 未認証の場合：`401`。

画面の初回表示や再読み込み時に、Hono RPCでこのAPIを呼びます。画面に保存するのは表示用のユーザー情報です。アクセスを許可する判断は、APIがリクエストごとに行います。

この章の終了時点では、現在の利用者を取得できます。メモAPIのアクセス制御は次の章で追加します。

## 手動確認

1. ログインして、レスポンスの `Set-Cookie` を確認します。
2. ブラウザにCookieが保存されたことを確認します。
3. `/api/auth/me` のリクエストにCookieが付くことを確認します。
4. ページを再読み込みしても利用者を取得できることを確認します。
5. Cookieを削除すると `/api/auth/me` が `401` になることを確認します。
6. DBの保存値が、ブラウザのトークンと異なることを確認します。

## 自動テスト

- 発行したトークンで、対応する利用者を取得できる。
- 未登録のトークンでは `null` になる。
- 同じユーザーに二つのセッションを作成できる。
- DBに保存されたハッシュ値をトークンとして渡しても、認証されない。
- 期限の前後で、仕様どおりの判定になる。

テストで数回異なる値が出ることと、乱数の予測困難性は別の確認です。乱数生成には仕様で指定した暗号用途のAPIを使っていることをコードでも確認します。
