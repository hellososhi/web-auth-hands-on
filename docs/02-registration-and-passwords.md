# 第2章 ユーザー登録とパスワード保存

[← 第1章 認証のないアプリを調べる](01-understanding-the-app.md) · [目次](README.md) · [第3章 パスワードを確認する →](03-verifying-passwords.md)

## この章の目標

`User` モデル、パスワードのハッシュ・照合関数、登録APIを作ります。この章の登録はユーザーを保存するところまでです。登録後は完了メッセージを表示します。

## 実装する仕様

- ユーザー名とパスワードを受け取る。
- ユーザー名は重複して登録できない。
- パスワードはArgon2idによるハッシュを保存する。
- ハッシュ化ごとに、新しいランダムなソルトを使う。
- 成功時は `201` と公開用のユーザー情報を返す。
- レスポンスにはパスワードとパスワードハッシュを含めない。
- 入力不備は `400`、ユーザー名の重複は `409` とする。

ユーザー名の重複は、登録時の入力を修正できるように通知する仕様です。このアプリではユーザー名をアカウントの識別名として扱います。ログイン失敗時の応答は第3章で統一します。

## なぜパスワードをハッシュ化するのか

平文のパスワードが保存されたDBを読まれると、パスワードそのものが分かります。保存用のハッシュは、入力の照合に使える形へ変換した値です。

攻撃者は候補のパスワードを計算し、保存値と照合して推測を試みられます。パスワード用のArgon2idは、この試行に計算時間とメモリを使わせます。高速なSHA-256をそのままパスワード保存に使うと、大量の候補を試しやすくなります。

**ソルト**は、ハッシュ化に加えるランダムな値です。同じパスワードでもソルトが異なると保存値が変わり、事前に計算した結果を使い回しにくくなります。ソルトは、保存用ハッシュ文字列の一部として扱えるAPIを使います。

参考：[OWASPのパスワード保存ガイド][ref-password-storage]

## 設計課題：Userモデル

以下を満たすPrismaモデルを設計してください。

- 各ユーザーを識別できる。
- ログインに使うユーザー名を保存できる。
- ユーザー名の重複をDBでも防げる。
- 保存用のパスワードハッシュを保持できる。

各項目について「何に使うか」「どの型にするか」「一意制約が必要か」を説明してからモデルを書き、マイグレーションを作成してください。

重複の確認をAPI側で行っても、同時に届いたリクエストが同じ確認を通ることがあります。DBの一意制約と、制約に違反した場合のエラー処理を組み合わせます。

参考：[Prismaのモデルと一意制約][ref-prisma-models]

モデルを書いたら、リポジトリのルートで次を実行します。

```bash
pnpm db:migrate --name add-users
```

このコマンドは `prisma migrate dev` で変更履歴を作成・適用した後、Prismaクライアントを生成します。生成先は `src/generated/prisma/` です。以後のAPIでも、テンプレートの `src/server/db/client.ts` で用意したDB接続を使います。

## 実装課題：ハッシュと照合の関数

`src/server/auth/password.ts` に、次の関数を実装してください。

```ts
// 関数の契約。実装は自分で書く。
declare function hashPassword(password: string): Promise<string>

declare function verifyPassword(
  password: string,
  storedHash: string,
): Promise<boolean>
```

テンプレートに入っている `argon2` 0.45.2 の `hash` と `verify` を調べ、これらの関数から呼び出します。暗号計算・ソルトを含む保存形式は、そのライブラリのAPIを使います。ライブラリ側と教材の関数で、引数の順序も確認してください。

照合するときは保存済みハッシュと入力パスワードを `verify` に渡します。`hashPassword` を再実行すると新しいソルトが使われるため、生成した文字列同士の単純比較では照合できません。

参考：[node-argon2のAPI][ref-argon2]

## 観察課題：同じパスワードを2回処理する

1. 同じ文字列を使って、`hashPassword` を2回呼びます。
2. 二つの保存用ハッシュ文字列を比べます。
3. 元のパスワードと、それぞれの保存値で照合します。
4. 誤ったパスワードでも照合します。

記録するのは、保存値が一致したかと、照合結果です。実際のユーザーのパスワードやセッショントークンをログに残す実装は作りません。

## 実装課題：登録APIと画面

`POST /api/auth/register` を追加します。

処理の順序は、入力検証、パスワードのハッシュ化、ユーザー保存、公開用データの返却です。登録フォームからHono RPCで呼び出し、成功時は登録完了メッセージを表示します。次の章でログイン画面を作り、その画面への遷移を追加します。

`User` のDBレコードを、そのままレスポンスに渡さないようにします。返す項目は `id` と `username` です。

参考：[Honoの入力検証][ref-hono-validation]

## 確認と説明

- [ ] 登録したユーザーがDBに保存される。
- [ ] パスワードの平文がDBに保存されていない。
- [ ] 同じユーザー名を登録すると `409` になり、ユーザーが増えない。
- [ ] 正しいパスワードと誤ったパスワードを見分けられる。
- [ ] レスポンスにパスワードハッシュが含まれない。

**説明課題：** ソルトの役割と、照合時に `verify` を使う理由を説明してください。
